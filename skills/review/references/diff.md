与逐文件通读不同，这里的分析对象是变更本身。以 diff 为对象可以省下大量上下文，代价是你看不到改动周围的全貌——所以每当一个结论依赖于"这段代码之外还有别的东西"时，必须停下来去追那块上下文，再回来定性。

**取输入时先看一遍未跟踪文件。** `git diff` 看不到它们（`??` 那几行），而本次任务新建的文件常常正是重点——只用 `git diff` 取输入，整份新文件会被静默漏掉。用 `git status --porcelain` 一并纳入，再开始。

本件负责调度。结构性与健壮性问题分别按 `references/code.md` 与 `references/robustness.md` 判断；**只改了配置 / 文档 / 依赖的变更集，再叠 `references/docs-config.md`**——可往返、未知字段被静默丢弃、依赖大版本升级这三类破坏在变更集上最常暴露，而它们是那一册才有的判据。这里只补充只对"变更"成立的那几类问题。

**先写一句作者意图，标成推断档。** 这份 diff 合起来想干什么——加错误处理、换算法、改名、补配置、还是升级依赖？写成一句，再写"什么会让我改判"。它是后面所有判断的上下文：判"这次改动丢掉了信息"之前，得先知道它想达到什么。**意图猜错会把整份评审带偏**。**落点在报告里**：并进 `停止审查的依据` 表之后那三行收尾之内，写成「意图（推断）：〈一句话〉」；**它不进 A 表、不占条目**。

**对抗册必载**（对象是代码实现或变更集）：`references/adversarial.md`；动不可逆状态再叠 `references/verification.md`；认得出语言或界面栈的，`references/lang/〈栈名〉.md` 也必载（没有清单走 `references/lang/method.md` 现场推）。**停止审查表里没有 adversarial 那一行的，结论最高只能到「待查」。** 依据、确认程度与「严重」的独立依据按 `references/contract.md` 第一、二节；本册只加一条：diff 对象常要两处原文合取，走该件第三节。
## 一、语义等价性

逐块比对改动前后的行为，而不只是看代码形式是否更整洁。

- 对外文案是否逐字符一致？提示语、错误信息、日志格式的细微改动会破坏依赖它的东西（包括测试和下游解析）
- 执行顺序是否改变？顺序改变往往在正常路径上看不出来，只在失败路径上暴露
- 控制流的改写有没有引入资源管理回归——提前返回、短路求值或错误传播是否跳过了原本一定会执行的清理步骤
- 边界条件的比较方向、开闭区间是否与改动前一致

## 二、倒退检测

新实现是否丢掉了旧实现携带的信息。这类问题不会让测试变红，只会让后来的人失去线索。

- 注释里的语义解释、错误分类、失败后的恢复指引是否被一并删除？这些是信息，不是噪音
- 某个类型原本有行为上的消费者，改动后还有吗？还是它变成了只被定义而无人使用
- 错误类型是否在改写中被压平成了字符串
- 原本被分开处理的几种情况，是否被合并成了同一条路径

## 三、连锁产物

- 改动是否让一部分代码变成死代码（按 `references/code.md` 的死代码条目判断）
- 调用点是否被误伤：签名或语义变了，但某个调用方没跟着改
- 类型约束是否被放宽：为了绕开某个障碍把类型改成了 any/动态/裸类型/更宽的接口，而放宽的理由只在本次实现内成立
- 测试是否因为改动而失去意义——还在跑，但已经不再覆盖它原本要覆盖的行为

## 四、注释与措辞

按 `references/discipline.md` 的注释标准检查，另外注意两件只在这里出现的事：

- 新增注释是否自然、纯描述，没有"修复了""原先""改为"这类只对本次改动有意义的措辞？读代码的人不知道也不关心它上一版是什么样
- 注释描述的是代码现在的行为，还是作者当时的意图？两者在改动后经常分叉（判据见 `references/code.md` 的"表达"一节）

## 五、上下文完整性

这是以 diff 为分析对象的主要风险。

偶尔会看到某处逻辑"不对称"或"放宽了"，孤立读这一段确实像缺陷。但在定性之前必须追到上游调用方和真正的闸口：**这个分支实际可达吗？** 先查清真实可达性，再决定要不要报，以及注释里该怎么写。

同一原则也适用于反向：某个检查看起来多余，可能只是因为你看不到它挡的那条路径。

## 六、结论的背书

关于行为等价性的任何断言，都要说清它由什么背书，以及这个背书覆盖到哪一步为止。

- 编译通过只证明它能编译
- 静态检查通过只证明它符合规则
- 测试全绿只证明没有测试碰到被你改动的路径，除非有证据表明那条路径确实被执行了——口径与这条例外见 **`references/contract.md`** 的"三条自检"

## 七、补丁味：这个修法是在修根还是在补洞

**只看形状，不看动机。** 作者是不是在补，不看他怎么说，看这次改动留下了什么痕迹——下面每一条都能指到位置，不是"感觉像"。

- **同一个不变量被两处各保证一次。** 新加的守卫与已有的那处判的是同一件事，**且两处处在同一个函数体内、中间没有改变被检值的语句**——跨边界或中间有写入的按 `references/code.md` 的"冗余"一节判，两册都不报。同一函数体内、中间无写入的，这不是"多一层保险"：它说明那个不变量没有唯一的家，下一处改动只会再多一处。
- **默认值被调用方逐个纠正。** 每个调用点都传同一个非默认值——默认值放错了层，该搬的是默认值，不是再改一遍调用方。
- **为绕开本地一个错误而加的检查。** 新检查挡住的，是本次改动自己造出来的状态。这类检查在原状下不成立，它是补丁的签名。
- **两处同名不同义。** 新加的"校验""清理""同步"与已有的同名，管的东西不一样——名字一样、语义两样，是把根问题藏进词汇里。
- **修完之后多了一条"必须记得…"的口头约定。** 没有强制点的规矩，就是下一条漂移源。

**两处以上出现同一条，就别在 diff 这一层结了**——挂到 `references/contract.md` 的决策点上，问它是不是同一个根、该修在哪一级。**补丁味本身不是缺陷，不定级**：它是"再往上问一层"的信号；把它写成一条发现，读者只会看到一堆风格意见。

**补丁不是要被消灭的东西。** 对一条补丁只问一句判据：**改完以后，下一次同类问题走的是同样的补丁，还是被结构挡住了？** 前者可以接受——补丁会一直来；后者才算这条补丁收敛。要求"没有补丁"只会让补丁藏起来。

## 收尾

报告的形态（固定三段、合并重复、改动不复述）以 **`references/contract.md`** 为准，本件不另立一份。这里只补一条**对 diff 特有**的：改动本身不要复述——它已经在 diff 里；你另做的、diff 之外的编辑单独列出，但不要把它写成收尾必备的一项。

## 关于修改代码

如果这次任务同时包含评审和修复，**把两者分开报告**。静默地一边审一边改，会让评审结论失去依据——人无法判断你报的是修改前还是修改后发现的问题。每一处改动都要能被单独指出并复述理由。
