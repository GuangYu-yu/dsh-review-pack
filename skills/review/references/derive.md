通用清单的问题是它按"平均的项目"写。它会问你这里根本不存在的东西，同时漏掉这里真正危险的东西——而后者才是你该花时间的。所以不要套清单，先测这个项目的风险面，再推出问题。

## 一条贯穿始终的判据

**凭空造出来的风险不是免费保险。**

一条对抗性问题如果并不成立，它不会安静地消失——它会被当成真实风险去对待，进而逼出防御性代码、多余的检查、以及为假想失败预留的分支，而那些分支本身就是过度工程化的来源。

所以推导出来的每一条，都必须能指到具体位置或具体后果。指不到的，删掉，不要留在清单里凑数。

## 第零步：先冻结问题

在讨论任何方案之前，把问题的边界写下来：**目标、约束、验收标准、不可接受的结果**。冻结的是边界，不是认识——认识可以深化，但每一次深化都要显式记下来，不能为了让方案成立而悄悄改问题。后面任何一轮发现"好像对不上"时，回到这一份来比。

同时声明**设计期禁区**：哪些东西永远不碰。禁区不是可讨论项，而是推导前提——拿它当约束反推解空间，而不是先出方案再评估风险。

如果评审对象已经带着一个方案来，先确认它服务的是不是这份边界，再往下走。

## 第一步：测风险面

不是问"这是什么语言"，那是没信息的——**语言相关的风险另有推导方法，见 `references/lang.md`**。这一步问的是**这个系统有没有暴露在下面这些面之下**，以及暴露得有多深：

| 面 | 有暴露的信号 | 没暴露的信号 |
|---|---|---|
| 外部输入 | 解析文件/网络/命令行/环境变量 | 只处理自己产生并回读的数据 |
| 持久状态 | 写盘、数据库、缓存、日志、检查点 | 纯内存、进程退出即结束 |
| 并发 | 线程、异步、多进程、多实例 | 单线程、单进程、无共享 |
| 外部系统 | 调 API、调外部命令、依赖网络服务 | 完全自包含 |
| 资源 | 持有句柄、缓冲区、连接、锁 | 短生命周期、无累积 |
| 状态机 | 多阶段流程、可中断、可恢复 | 一路到底、无中间态 |
| 数值 | 偏移、长度、容量、时间、精度 | 只做逻辑判断 |
| 权限 | 提权、多用户、跨信任边界 | 单一信任域 |
| 版本 | 数据格式、协议、兼容承诺 | 只和当前版本自己打交道 |

做这一步靠读，不靠猜。**读的是证据源；证据源随对象形态而变**：

- 对象是代码 → 入口点、持久化调用、线程/任务创建、解析器、错误类型定义
- 对象是文档、契约或指令 → 它承诺了什么、引用了什么、哪些章节被别处当依据、哪句话是断言而非事实
- 对象是配置或数据 → 谁读它、哪些值会被下游当索引或边界、缺失与非法值的处理在哪

**把结论写成"哪些面有暴露"，不写成"这个项目很复杂"。**

这张表只是**检索线索**，不是清单本身。最终审查项必须写成本项目里能指到位置或后果的条目；只对上了表格某一行、却指不到位置的，不成立。

## 第二步：只对真正深暴露的面展开

对每个判定为"有暴露"的面，展开它的问句：

- **外部输入** → 每个进入的字段，下游拿它做索引/算长度/比容量吗？解析处的界与下游的假设一致吗？畸形输入走哪条路？
- **持久状态** → 多段写入的中间态各是什么？任意落点中断后，重新读入会看到什么、选中哪一份？
- **并发** → 检查与执行之间的窗口里，第三方能改什么？交错的顺序里哪几种会让前提失效？
- **外部系统** → 超时是实测的还是猜的？重试幂等吗？对端行为假设（编码、顺序、必填字段）验证过吗？
- **资源** → 哪条路径可能不释放？释放两次会怎样？用了已释放的？
- **状态机** → 判定的全部组合里，有没有哪个被当成全新作业？恢复逻辑用的是从持久状态读回的预期，还是自己算出来的？
- **数值** → 边界是开区间还是闭区间？溢出、截断、精度损失后下游还成立吗？
- **权限** → 默认是拒绝还是允许？假设了某个外部机制存在吗？它失效时怎样？
- **版本** → 新旧共存期读写行为确认过吗？破坏时的表现是什么？

**这一步是本件最容易退化成通用清单的地方，所以它的闸门比段落本身重要：**

先写下每个"有暴露"的面在本项目里的**具体位置**，指不到位置的整个面不进入。只对留下的面展开问句。

一个正常的项目，真正深暴露的面通常是个位数——多数面只是浅暴露（"有持久状态"但只写自己的日志），浅的不展开。**如果你把九个面全展开了，说明你没能把"有暴露"和"深暴露"分开，本件就退化成了它开篇反对的那种清单。**

## 第三步：装订成可验证的条目

推导出来的每一条都要落到下面四种形态之一，否则它不是一条可执行的审查项。**括号里只是"什么叫落到形态"的刻度，不是待核对的清单**：

- **一个具体位置**（文件与行，或文档的章节与句子）
- **一个能描述出来的失败场景**（谁的什么输入或时序，导致看见什么错的结果）
- **一条现有测试或校验没覆盖的路径**
- **一个可执行的确认动作**（跑一次、加载一次、查一个值）

这四种是**代码类对象的实例**，不是穷尽。被审对象是文档、契约、指令或配置时，"位置"就是行号或章节，前两种形态换成"哪一句与哪一句冲突""哪一种输入会让它给出错误指引"。**一般判据始终是前面那条**：能指到具体位置或具体后果。

## 第四步：定序

按"错了会不会静默"排序，不按"重不重要"排序。

静默的错误、静默的截断、静默的降级、以及**信息不足却放行**，排在最前——它们不会报错，只会在很久以后以无法解释的形式出现。会立刻崩的错误排最后，因为它自己会喊。

## 收束闸门

推导必须有个头，否则它会变成一份自产的通用清单。三条闸门：

1. **只保留高暴露面。** 浅暴露的面不进入本次审查。全都要审等于没有重点。
2. **成本对价。** 每提一条**要求改动的建议**，问一句：为它增加的复杂度，换来了什么具体故障的避免？答不上来的，不提。

   "改动建议"是本条的射程。**"查了但确认没问题"的负向结论不受它约束**——那是负向结论，不增加任何复杂度，反而必须报出来。不要把这条读成"只想得出风险才准写"。
3. **区分"还没实现"与"设计上不支持"。** 这两者对未来改动的含义完全相反，混在一起会让人误判这是欠债还是约束。判断方式见 `references/reasoning.md` 的"系统的边界与完备性"。

**这四步是推理顺序，不是运行时阶段。** 某一步对本对象不适用时可以跳过，但要在报告里写明——否则"判定为不适用"和"忘了做"长得一模一样。**"成本对价"这条闸门同理**：判定为不适用时写明理由，而不是默默绕开它。

## 顺带要产出的东西

推导的过程本身就是一次价值审计，顺手记下两样：

- **明确排除的复杂度**：本来可以做、但确认不需要做的事，以及原因。写下来能防止后来的人重新提议。
- **仍然纯属推断的结论**：哪些判断没经过实测。不是所有推断都要立刻验证，但要标出来，并在其中找出最该先验的那一条——通常不是最难的那个，而是最没被检查过的那个。

判断这份推导够不够格，看同一个信号：**写出的"不审什么"和"保留什么"是不是同等具体。** 说不出"不审什么"，就说明还没真正理解这个项目。

## 报告

本件产出的是一份待查清单，它同样要按 入口件第三节（每条结论都要能核对）交付：

- 风险面测定本身也要标证据档位——哪些面是读代码确认的，哪些是推断的。测定是后面三步的输入，输入错了，后面全错且没有任何信号
- 清单的"仍然纯属推断的结论"正好对应契约的**第 1 项（档位）**，不要与"实测过的"混在一起写
- 写明这次依据什么判定某几面"低暴露、不审"

**证据档位要落到"来源"，不是"我感觉有多确定"。** 每一条推导出的条目都要能说出它的依据在哪：读到的哪一行、注释里的哪句承诺、还是你的推断。推断类条目不要与读出来的混在一起排——**排在一起会让推断看起来像结论**。

## 当审查对象只是系统的一个片段

这是本件最容易产生高级误报的地方。只读一个文件时，凡是**依赖片段之外才能判定**的条目（"如果上游没做 X""如果调用方漏了 Y""如果这个类型在实际路径上……"），都只是候选，不是发现。它们看起来比普通猜测可信，因为它们有推导的形状——但形状不是证据。

所以：

- 把这类条目**单独归为一组**，标明"判定依据在目标之外，需读 X 才能定性"
- 在报告里说清**这个片段的边界在哪**：它被谁调用、它承诺的事在哪里兑现、它的前提由谁保证
- 如果这些位置恰恰是缺陷所在（很常见），那就说明**片段不是合适的审查单位**——先扩大范围，或者至少把这一点作为首要结论写出来

反过来也要小心：片段内部的条目若依赖外部语义（例如"这个 API 应该会报错"），同样需要出处。

## 推导出的条目分两类：查得到的，和要查的

同一个"查证"规则，两类条目的做法完全相反——搞混就会白烧 token 或放过误报。

**第一类：依据在被审对象内部。** 上游做了什么、调用方漏了什么、这段承诺在哪里兑现——**必须去读，不要凭印象**。

这类是误报的主要来源（本件最典型的失败就是把"我没看到"当成"它没做"），而它们的证据**就在同一个仓库里，最便宜**。读完一句话的事。

**第二类：依据在语言语义、库行为或版本差异上。** 判定这类条目之前，先过一道闸门：

| 情况 | 做法 |
|---|---|
| 答案在你确有把握的知识里 | 直接用，标为"语言语义" |
| 你不确定，或这个事实**可能随版本/平台变过** | **去查一手来源**，再报 |
| 该知识点查不到权威出处 | 不要报成发现，标为"待验证的假设" |

判据是这一句：**如果这条判断错了，会是因为什么？** 答案是"我没读完代码"就去读代码；答案是"我记错了这个行为"就去查规范。

这条闸门不是每一条都要走——**在模型确有把握的领域查规范，是拿 token 换已有的东西**。它只在上面第二、三行那两种情况下生效。

引用来源时按入口件第三节的四个档位（亲读 / 实测 / 权威文档 / 推断）分开写，不要混排——把推断和亲读排在一起，会让推断看起来像结论。

## 选件与覆盖边界

对象分发表由入口件持有，本件不重复。下面是**表里看不出来的边界**——拿不准选哪册时看这里。

五处容易混的边界：

- **只描述症状**（"拿锁之后 await 了一下""这里 clone 得有点多"）仍是语言语义 → `references/rust.md`；时序窗口与多段写入中间态 → `references/adversarial.md`。
- 把"会不会被搞坏"的**推理**写出来 → `references/adversarial.md`；把它变成**可执行的验证与判据** → `references/verification.md`。
- 问"我是不是有什么没验证到"（准备宣称完成、要把关）→ `references/discipline.md`；问"该测什么、按什么判成功"（要一套验证方案）→ `references/verification.md`。
- 只查"写的和实际是不是一回事" → `references/docs-config.md`；判断一个方案值不值得采用 → `references/style.md`。
- **不知道从哪查起**（新接手项目、团队没有项目级清单）→ 本件（`references/derive.md`）；只有"这门语言本身没有现成清单、要为它推清单"才用 `references/lang.md`。两者同时沾边时，先由本件定该查什么，再由 `references/lang.md` 补语言特有的面——"接手一门没有现成清单的语言的陌生项目"就属于同时沾边：**两册都读**。

**没有对应分册的对象**：先按本件推导该审什么，再按对象分发或补位，**不要假装被覆盖了**。
