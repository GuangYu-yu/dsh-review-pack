## 先跑工具链，工具链报的不写进本件

`cargo clippy --all-targets -- -D warnings` 覆盖这些（**组别与默认级别以你机器上那版为准**——`clippy-driver -W help` 会把它那份列出来）：`ptr_arg` / `let_and_return`（`&String` 参数、尾表达式返回 let 绑定）、`single_match` / `redundant_pattern_matching`、`derivable_impls`、`await_holding_lock`、`manual_filter_map`、`not_unsafe_ptr_arg_deref`（默认 deny）、`undocumented_unsafe_blocks`（需显式开启）。

rustc 自己就报的同样不列：未使用的生命周期参数（E0392）、迭代中修改集合（E0502）、非 `Send` 跨线程或跨 await、`unused_must_use`、公共 API 泄漏私有类型（`private_interfaces`）。

## 所有权与借用

- 函数的最后一条表达式是克隆，而克隆出来的值只用于返回：通常说明签名该收所有权，或者返回值该借用
- 签名接受所有权参数，函数体内却只做只读操作：调用方被迫放弃了它本来还能用的值。不报：签名由 trait 或既有约定定死，改不了
- 用 Box 做了堆分配，但值的生命周期完全可以确定在局部作用域内。不报：这个值需要稳定地址（被 `Pin`、或要交给 FFI）

## 错误处理（语言机制部分）

- 库代码里，把**调用方传入的参数**会触发的可恢复错误处理成 unwrap 或 expect——把调用方的问题变成了它自己的 panic
- 同上条件下使用 panic!。注意正当的例外：文档里已把 panic 写成契约、违反内部不变量、以及测试代码，这些都不报
- 公共 API 返回裸 Result，没有定义自己的错误类型，调用方无法稳定地区分失败原因。不报：函数是二进制内部的，不构成对外 API
- 用 String 当错误类型，丢掉了分类和结构化上下文。不报：调用方不需要匹配这个错误，只记录或展示
- 错误转换时经过一次 to_string，原始错误类型在那一层就再也拿不回来了。不报：这个错误在这一层之后只用于展示
- 同一错误类型的转换散落在多处手写，没有统一到 From 或 Display。不报：各处转换取的字段子集本来就不同，它们不是同一个转换

## unsafe

- 存在安全替代方案时仍然用了 unsafe。不报：**证明不了**安全替代能达到同一性能——那要实测，不是读代码能定的
- unsafe 块没有以 SAFETY 注释写明其成立前提。不报：SAFETY 写在外层（函数级）注释里，且块内没有多余的行
- unsafe 块覆盖了块内并不需要 unsafe 的行，把安全代码也划进了审计范围
- 手写 `unsafe impl Send` / `Sync` 而没有逐字段论证（字段含 `Rc`、`Cell`、`UnsafeCell`、裸指针时尤其）：`Send`/`Sync` 是编译器对并发唯一的静态证据，声明错了此后没有任何检查。不报：类型是单字段的新类型包装，且该字段已知 `Send`/`Sync`
- FFI 返回的原始指针直接交给调用方，没有封装成安全抽象。不报：指针的生存期已写进调用方的契约

## 类型与模式匹配

- 同一业务语义在不同位置用了不同的基本类型。不报：这些位置之间不交换数据
- 公共接口的 Option 参数，导致调用点到处传 None 而无法自明
- 同一个值在模式里被重复绑定，可以用 @ 合并
- From 或 Into 的实现丢掉了承载业务语义的字段——当两侧类型表达同一业务概念、而未使用的字段在下游无从取得时，这个转换要么不完整、要么本身就不该存在。仅取子集的视图类型转换是正当的，不报

## trait 与泛型

- 公共类型没有实现它本该实现的常用 trait，导致调用方到处写适配代码。不报：实现它需要的信息这个类型里没有，写出来只能是错的或 panic 的
- 用 Box<dyn Trait> 做参数或返回值，而所有可能的实现类型在编译期就已经确定。不报：`dyn` 是为了**一个容器装多种类型**，不是为了替换实现
- 泛型参数约束了 'static，而实际传入的引用并不需要它，白限制了调用方。不报：值会被存进需要 `'static` 的地方（`spawn`、`static`）

## 并发与异步

- 异步运行时是多线程调度时，在异步函数里调用会阻塞的标准库同步 IO（std::fs::File、std::net::TcpStream 等）。单线程本地执行器下没有这个问题，不报
- spawn 出来的任务，其 JoinHandle 被丢弃，于是任务的失败和 panic 无人处理。不报：任务是进程级单例，失败即整体重启
- 同一作用域内多次调用 borrow_mut 或 borrow，导致借用重叠——通常是把借用范围写得太长，而不是真的需要多次借用
- `async` 块或异步函数定义后从未被 `.await`、也从未被 spawn：它要么是死代码，要么是漏了执行——必须能说出是哪一个。不报：它是公开 API 的一部分，由调用方决定要不要 await
- 用 `Rc<RefCell<T>>` 搭共享可变状态，而该值从未被多个所有者持有：那是把并发原语当成了绕开借用检查的工具。不报：类型是公开 API，外部可能持有第二份
- **取消安全**：`select!`、`timeout`、竞速分支放弃一个 future 时，它可能停在任何 `.await` 点。判据是"这个 future 被丢弃时，**已经扣掉的进度、拿到的资源、写了一半的状态**由谁收拾"——`Drop` 覆盖了什么，并发原语（`Mutex`、信号量、许可）在取消路径上是否已释放。拿不出结论的，就把"哪些 future 是对取消安全的"写成必须公开的契约（逐条标注），而不是留给调用方猜

## 集合与迭代

- 对迭代器 collect 出临时集合并立刻再 iter() 转回去，这次往返没有必要。不报：中间那个集合另有用途（要先拿 `len()`，或要用双端迭代）
- 为了绕开借用检查而 clone，但克隆出来的值在后续作用域里从未被修改——顺序调一下就不需要克隆。不报：克隆很便宜（`Copy` 或小 `Arc`），或借用跨了函数边界、顺序调不动

## 宏

- 同一模式重复出现三处以上，而函数或泛型无法表达它（需要展开成不同语句、或需要生成标识符）时才考虑提取成宏。宏是比函数更重的抽象，够不上这个门槛就不要提。不报：这几处的模式在演进方向上不同，将来会分叉
- 声明宏或过程宏生成的代码带上了调用方没有预期的 trait 约束或类型限定——这类约束应该由调用点决定。不报：该约束正是宏要保证的不变量，且已写进文档
- 派生宏对类型名或字段名存在**隐式命名约定**（按名字推导行为），而约定只活在宏的实现里、没写进文档：改个名字就静默改了行为。不报：约定由被生成的 trait 定义强制——改名会编译失败，不会静默

## 构建开关与校验

- `debug_assert!` 在 release（`-C debug-assertions=off`）下**根本不执行**，却常被当成真校验写进业务路径；`assert!` 才一直生效。不报：该断言只做开发期检查

## 可见性与接口

- 仅为了测试而放开的接口使用了 pub，而不是 pub(crate) 或 #[cfg(test)]。不报：外部集成测试（`tests/` 下）必须导出
- pub use 重导出时把内部模块的路径结构一起暴露了出去。不报：该路径本来就是稳定的公开入口（例如 prelude）

## 构建与依赖

- 依赖启用了默认特性集，而其中有一部分在项目里并未使用且可以关掉。不报：关掉它会改变语义（默认特性不是可选项）
- 同一个 crate 特性的条件编译判断在多个模块里各写了一遍，两份逻辑会漂移。不报：两处判断的是**不同**的特性
- 公共 API 里用类型别名暴露了第三方 crate 的具体类型，等于把依赖固化进了接口
- 依赖声明了但代码里没有引用它的任何项（rustc 不报这个，得靠 `cargo-udeps` / `cargo machete`）：白白拖长构建，也扩大了供应链面。不报：它是 build/dev 依赖，或只被 feature 门后的代码用到

## 已知盲区：三问与三道交叉检查在这门语言上会漏掉的面

**这张表是本册自己的，不是方法件的**——它是三次推导一致指出、三问与交叉检查都到不了的那批（口径见 `references/lang/method.md`）。推导完先拿它对一遍，比再补一轮条目更省。**每个栈各自推自己那张。**

- **异步与地址稳定性**：`Future` 的 `Send`、`!Unpin` 与 `Pin` 的自引用前提、`select!`/`timeout` 的取消安全
- **并发原语**：原子内存序（`Relaxed` vs `Acquire`/`Release`）、`OnceLock`/`LazyLock`、无界 channel、锁序、持锁做 I/O
- **数值与域语义**：溢出（debug panic / release 回绕）、`as` 的截断与符号、浮点 NaN 与比较
- **panic 与析构**：`panic = abort` 与 unwind 的差异、`Drop` 里 panic、`catch_unwind` 之后继续使用
- **布局与 ABI**：`repr(Rust)` 无布局保证、niche、字段顺序、`repr(packed)`
- **构建与供给链**：`build.rs` 与过程宏在编译期执行、锁文件漂移、feature 组合
- **分配与常量求值**：分配器不匹配、OOM、`const` 求值中的 UB

## 官方契约的常咬点（不保证覆盖）

标准库**契约**层面的咬人处——形态见 `references/lang/method.md` 的「官方契约那一层」。**每条都是 rustc 1.96.0 本机实测**（用 `rustc -V` 复查）；这里没写的当场查原文。

- **`String`/`&str` 的 `len()` 是字节数，不是字符数**（实测：`"héllo".len()` 是 6、`chars().count()` 是 5）——按"字符"算长度、按长度切片、按长度排列宽，全都会错。不报：长度只用于比较相等或预分配容量
- **切片按字节边界**：`&s[0..2]` 落在非 ASCII 字符中间会**运行期 panic**（实测：`byte index 2 is not a char boundary; it is inside 'é'`），不是取前两个字符。不报：索引来自 `char_indices()` / `find()` 这类本来就按边界给出的位置
- **整数除法与取模向零截断**（实测：`-7 / 2` 是 `-3`、`-7 % 2` 是 `-1`）——负数上的分页、取模分桶、余数判零都会偏；要向下取整得用 `div_euclid` / `rem_euclid`。不报：操作数已证非负
- **`Duration::as_secs()` 向下取整丢子秒**（实测：1999 ms → `1`）——要精度用 `as_millis()` 或 `as_secs_f64()`。不报：这个时长本就按整秒语义使用
- **`HashMap` 的迭代顺序不保证、且逐实例不同**（实测：同样内容两个 map 的 `keys()` 顺序不同）——依赖顺序就是依赖随机；要稳定顺序用 `BTreeMap`，或先排序。不报：只做查找、从不迭代
- **`f64` 转整型是饱和转换**，不是回绕、也不是 UB（实测：`f64::NAN as i32` 是 `0`、`1e20 as i32` 是 `i32::MAX`、`-1e20 as i32` 是 `i32::MIN`）——它**不 panic**，所以溢出会被静默吃掉。不报：转换前已显式检查过范围
