## 轴：定义点与使用点唯一性

同一语义在系统里存在多个定义点，或多个来源不同的使用点，或定义点缺失。

轴在时间上同样成立：旧组件硬编码值、新组件引令牌，即两个定义点。不报：新旧组件并行是文档声明的迁移策略。

**定义点在哪随技术栈变。** Web 的常见位置：CSS 变量（`:root` 与组件内 scoped）、Tailwind（`tailwind.config` 与内联 arbitrary value `[12px]`）、CSS-in-JS（`theme` 对象与 inline style）、令牌文件（**DTCG JSON** 是这个格式的标准）与生成出来的 CSS 之间、组件库的主题层与组件自身覆盖（slot、`::part`、`!important`）、JSX `style={}` 与样式表之间。

## 定义点与消费来源

这里同时问两件事：**同一语义被声明了几次**，以及**每个消费处的值从哪里来**。两者常常一起成立，所以合在一节里判；报的时候说清命中的是哪半。

- 同一语义有两个令牌名（`--green` 与 `--color-success` 指向同一色值）。不报：两者语义不同，只是色值相近
- 同一语义在两个作用域各定义一次（`:root` 与组件内各写一份）。不报：组件内那份是有意覆盖外层
- 同类元素使用不同定义点（组件 A 硬编码 `12px`，组件 B 引用 `--r-md`）。不报：多套值对应不同语义层级
- 排版组合（字号 × 字重 × 行高）未收敛到一组，同一视觉层级在两处各自组合。不报：组合差异是有意区分层级
- **值相同但来源不同**（`.panel { border-radius: 10px }` 与 `.card { border-radius: var(--r-md) }`，而 `--r-md: 10px`）：视觉上看不出来，改一处不会同步另一处。不报：裸值那处是一次性取值
- 同一令牌的消费点分散在过多文件，改动影响面不可控。**判据**：同一个令牌被 5 个以上文件直接消费，或跨 3 个以上技术层（CSS／JS／模板）各写一份——数得出来才算，数不出来不报。不报：消费点数量已文档声明为可接受范围
- **同一语义在不同技术层各定义一次**——断点写在 CSS 媒体查询里、同一个阈值又在 JS 的 `matchMedia` 里；配色模式在 CSS 与 JS 各判一次；动效参数在 CSS 与 JS 各写一份。**本条需人工确认语义等价**：grep 只抓得到文本相同，抓不到"这两处说的是同一件事"。不报：其中一处是从另一处派生的单一来源

## 状态语义

状态矩阵应当是全系统（或组件族）的**一份定义**，各组件引用它，而不是各自重写。

某元素的可达状态由它的交互模型决定。Web 表单 / 列表的示例：default / hover / focus-visible / active / disabled / loading / error / selected / readonly。其他场景另有状态（富文本：dirty / saved / conflict；画布：dragging / resizing / snapping；媒体：buffering / seeking / ended）。本册以该元素实际交互模型下的可达状态集为准。

- 可达状态未在某一定义点全部覆盖：定义了 hover 却未定义 focus-visible，或反之
- 两个状态在同处定义且相互覆盖（disabled 与 hover 同时命中，谁生效取决于选择器顺序）。不报：优先级已由显式声明（如 `:not(:disabled)`）锁死
- `loading` 状态下控件仍可再次触发，状态与行为未在同一处定义。不报：重复触发是幂等操作
- 状态的表现分散在多处（边框在组件内定义、颜色在主题内定义），改一处不生效。不报：状态表现全部收敛在组件自身的定义点上

## 层级

- `z-index` 分散在多个组件中定义，弹窗被下拉菜单遮挡。不报：层叠顺序已由统一的层级表定义，且组件只引用层级表中的值

## 结构语义

- 同一交互控件使用不同元素（`<button>` 与 `<div role="button">`），行为与可访问性不一致。不报：元素选择受框架或第三方组件约束
- 可访问名称来源不唯一（有的来自可见文本，有的来自 `aria-label`，有的来自父级），屏幕阅读器读法不同。不报：名称来源规则已在组件约定中统一
- 图片 `alt` 的语义层级不一致（有的描述内容，有的复述文件名，有的留空），同一类图片读法不同。不报：图片为装饰性，且已统一 `alt=""`

## 系统偏好语义

- `prefers-reduced-motion` 未定义，动效无法关闭。不报：动效已文档声明为必要交互反馈，且已提供手动开关
- 高对比度模式（Windows High Contrast、`forced-colors`）下图标、边框、背景被系统覆盖，可见性未单独定义。不报：界面明确不支持高对比度模式
- 深色模式被当作色板反转，图片、阴影、透明叠加、品牌色未在暗背景上重新定义。不报：深色模式已按独立设计定义

## 内容语义

本节按**文案、格式、状态呈现、反馈形式**这四类审。

- 同类操作的文案动词不收敛（"保存" / "确定" / "提交"）。不报：动词差异对应不同操作语义
- 同一类数据在不同位置显示格式不同（日期、数字、货币）。不报：格式差异对应不同区域或语言
- 状态呈现不收敛（每个页面各写各的 spinner、各写各的"暂无数据"、各写各的错误页）。不报：差异对应不同的容器尺寸
- 反馈形式不收敛（有的 toast、有的 inline、有的弹窗）。不报：形式差异对应不同的操作影响范围，且反馈规范中有对应条目
- 表单的验证时机、错误位置、必填标记不收敛，同一类字段在不同表单里行为不同。不报：差异对应不同的提交模型

其他领域（内容产品、电商、游戏、社交、财务）的对应条目按这四类归位；**归不进去的，算本册未覆盖**——四类不是穷尽。

## 官方契约的常咬点（不保证覆盖）

轴不止"定义点唯一性"——**平台规范定死的初始值与适用对象**也是同一类咬人处（形态见 `references/lang/method.md` 的「官方契约那一层」）。**每条都引规范原文**（MDN 的 CSS 参考，每页都带 Formal definition 表；`Format` 与规范版本见该页）。这里没写的当场查原文。

- **`box-sizing` 的初始值是 `content-box`**（"the initial and default value as specified by the CSS standard"，此时 `width` 只含内容，不含 padding 与 border）——**但 UA 样式表对 `table`、`select`、`button`，以及 type 为 radio / checkbox / reset / button / submit / color / search 的 `input` 用的是 `border-box`**。于是**同一个页面里两类元素的"宽度"含义不同**：给它们设一样的 `width` 并不一样宽。不报：全局已统一 `box-sizing`
- **百分比 `padding` 与 `margin` 都相对包含块的 `width`**（规范原文 "refer to the width of the containing block"）——**上下方向也不例外**，不相对高度。让一个按高度比例留白的块，或让同一行内几个盒子的上下留白随容器宽度变，都会得到意料外的值。不报：该处的百分比在同一容器宽度下取值，且已按此验证
- **`min-width: auto` 是个会变形的值**（初始值 `auto`）：规范原文说它对**块盒、行内块与表格布局盒解析为 `0`**，而对 **flex item 与 grid item** 用的是建议尺寸或 **min-content**——**同一个 `auto`，两种 display 下是两个不同的下限**。这正是"flex 里那一条内容撑破容器、怎么设 `width` 都不缩"的机制。不报：该元素不是 flex/grid item，或已显式写明 `min-width: 0`
- **`z-index` 的适用范围比"只作用于定位元素"宽**：普通 `position: static` 的块元素上确实不生效，但 **flex / grid 的子项即使 static，`z-index` 非 `auto` 也生效**（并建层叠上下文）。层级表里分了值、元素却三类都不是，才是整表失效，而不是"取值被忽略但仍在比较"。不报：该元素或其定位上下文已由层级表统一管理
