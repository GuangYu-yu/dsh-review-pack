语言清单最容易被写成一张经验表——"见过出问题的写法"堆在一起。那张表在写它的那门语言里好用，换一门就失效，而且要不停补。

换一个做法：**从语言的设计承诺推出它的典型缺陷。** 这门语言保证什么，它为兑现这个保证牺牲了什么，它开的逃生舱在哪——缺陷长在这三者的交点上。

## 先说清这套方法能做什么、不能做什么

**能做的**：决定你去问哪些问题、砍掉本来会写的东西、给每条发现一个"正当用途"的对照面、并在固化前先做一次收敛检查。

**不能做的**：它不产生语言知识。三个问题的**答案**来自你对那门语言的了解，本件只是规定了问什么、以及哪些不许写。

所以不要把它当成"不用懂这门语言也能审"的工具。它是**组织与过滤**的方法，不是知识来源。

## 三个问题，按顺序问

**这门语言已经有清单时，先读它的几个小节标题**——那是别人跑出来的方向（`references/lang/rust.md` 的「所有权与借用」「unsafe」「trait 与泛型」，就是 Rust 的三问答案）。照着标题走，比从零推稳。**标题本身就是种子，不必另抄一份**——抄一份就是同一件事写两遍，而且它会和标题各自漂。

### 一问：这门语言保证什么，因此它不让你做什么？

列出它用类型系统或运行时挡住的东西。这些保证的代价，就是这门语言里**最别扭的那些写法**。

别扭之处就是缺陷高发区，因为人在被挡住时会找最省力的绕法：

- Rust 挡住悬垂引用 → 最省力的绕法是 `.clone()` → 于是无谓克隆成了头号问题
- Go 挡住未使用的变量和 import → 最省力的绕法是 `_ = x`、空白导入 → 于是被丢弃的错误成了头号问题
- Python 用动态类型换灵活 → 最省力的是不写任何校验 → 于是边界处的类型假设成了头号问题

**接着问下去**（问句是固定的，答案才是这门语言的）：这门语言最挡人的三个检查是什么？每个检查最常被人绕过的写法是什么？那个写法在什么场景下会产生后果？后果落在哪一类——内存、并发、错误、性能，还是边界假设？

**在代码里定位**：找的不是"错"，是**"为了过检查而加的东西"**——`clone`/`copy`/`as`/`unwrap`/`any`/`void*` 这类动词出现在不该有的密度上；以及本该由类型承载、却被拆成字符串或 `bool` 的那几处边界。

### 二问：它替你抓什么，因此哪些它抓不到？

这道题决定**哪些条目根本不值得写**。

编译器、类型检查器、linter 会报的东西不要进清单——它们自己会喊，写进去只是让报告变长。

清单只该装**工具链抓不到、但人会后悔**的那一类：能编译能跑，事后才知道错了。所以在动手列条目之前先写下："这门语言里，哪些错误是它**不会**替你抓的？"

常见四类：纯性能问题（多余克隆、GIL、切片别名）、语义正确但意图错误（错误被吞成默认值、断言掩盖真实形状）、跨边界后的假设（编译期类型在运行期数据上不成立）、生命周期与顺序（事件循环被同步调用堵住）。

**接着问下去**：这门语言的工具链目前**最可靠**覆盖的是哪几类？剩下那几类，在这份代码里以什么形式出现？有哪一类错误是"编译通过、测试通过、**事后才知道**"？

**在代码里定位**：去工具链够不到的地方——跨进程/跨网络的边界、`await` 之后重新读取的那个世界、被一个 `try` 包住的整个函数体、只在失败时才走的分支、以及只在生产数据量下才成立的假设。

### 三问：它的逃生舱在哪？

每门语言都有一组"为了让你能干活而开的口子"，这些口子在压力下会被当成常规手段用。常见形态：强制类型转换、`any`/`interface{}`/`void*`、unsafe 块、动态代码求值、字符串拼接出的查询、反射、绕过可见性的后门。

对每个逃生舱问：**它的正当用途是什么？这个用法属于正当用途吗？**

- Rust 的 `unsafe`：正当用途是 FFI 与已证明的不变量；不正当是"编译器不让，我偏要"
- Go 的 `interface{}`：正当是真正的异构容器；不正当是"我懒得定义类型"
- Python 的 `getattr`：正当是通用框架；不正当是"我绕开这个类的接口"

**接着问下去**：这门语言有哪几个口子？每个口子的正当用途是什么？**这一次用法**属于正当用途吗？不正当的用法通常出现在什么压力下——时间紧、类型难表达、要跨边界？

**在代码里定位**：每个逃生舱的**每一个**调用点都要落到具体位置，然后对那一个调用点问一遍"它的正当用途是什么、为什么这次不是"。指不到调用点的，不写。

**一次完整的走法**（拿 `references/lang/rust.md` 里已经有的那条走一遍，说明条目是怎么被问出来的）：一问答"Rust 用借用检查挡住悬垂与数据竞争" → 接着问"最常被绕过的写法" → `.clone()` → 问"什么场景下会产生后果" → 每帧都在克隆一个大的 `Vec`，或者为了让借用检查通过而克隆出一个**逻辑上本该共享**的对象 → 问"后果落在哪一类" → 纯性能 + 意图（克隆把本该共享的设计盖住了）→ 落成条目**无谓克隆**，并配一个正当用途的对照面（跨线程转移所有权时克隆是对的），条目里那句"不报：值确实需要独立所有权"就是这么来的。

## 三道交叉检查

推完上面三个问题后，再过三道，用来抓那些不属于任何单一类别的条目：

**哲学与便利机制的冲突。** 语言的设计哲学和它最顺手的语法糖经常不在一边，冲突处就是错用高发区。

- Rust 哲学是错误要显式传递；但 `?` 让传递变得太机械，于是人会用 `?` 传上去却不再判断这个错误该不该分类处理
- Go 哲学是显式；但 `if err != nil` 模板化到可以盲写，于是错误被检查了但没被处理

**形式满足。** 某个机制要求你做一个动作，动作被做了但内容没有。

- 实现了 `From`，但没把源类型的字段真正用上
- 实现了接口，但方法是空的
- 加了 `#[derive(Debug)]`，但字段全是不可读的 id

**工具链的盲区。** 最后一类不属于设计承诺，而属于"这门语言的工具生态不管你"。问一句："这门语言的运行时模型，有哪些行为是编译器看不见的？"这类要单独想，因为它不由语言语义推出，而由运行时模型推出。

## 怎么用

不要把推出来的东西当成通用清单再用一遍。推出来的每一条仍然要落到具体位置：

- 这个逃生舱的这一次用法，正当用途是什么，为什么这次不是
- 承诺在这个场景下真的成立吗（编译器信了，运行时呢）
- 工具链抓不到的这一类，在这份代码里的具体位置在哪

推不出来、指不到位置的条目，不写。

## 固化之前先做收敛检查

对同一门语言推导两次——**第二次换一个入口起手**（例如第一遍从"保证什么"起，第二遍从"逃生舱 + 运行时模型"起），看命中的是不是同一批问题。**只重合一半也算没收敛**；两次推出完全不同的东西时，不要急着把它固化成清单。

**复现口径（Rust，同一模型，3 次独立推导）**：两次不同入口的推导，与一份现成 Rust 清单逐条比对，重合约 19%–43%；3 次推导共同命中的只有约 14 格、折合 6–8 条；约 30% 的格子在两次之间判定直接相反（同一段 `unsafe`，一次记"有缺陷"、一次记"无"）。

**这组数字来自单语言、单模型的实测，用来支撑"两次不够"这一个结论，不可外推**成其他语言或其他模型上的预期重合率——有意义的不是那个比例，而是"它低到不能靠两次"。由此得到两条硬要求：

- **至少 3 次独立推导取交集**才算收敛。两次不够；单次内部"走两遍再取交"更不算——两遍由同一批先验驱动，只证明自洽，不证明可复现。
- **裁决规则必须同时固定**：同一条形状记到哪条保证下、跨类的形状怎么合并、边界情况算不算缺陷。规则不固定，重合度不会随推导次数提高。

收敛 → 固化成该语言的清单（放本目录），标为**稳定核**；不收敛 → 不固化，每次现场推导。**先固化成候选也行，那就标为候选池**：清单自己在文件开头写明是哪种，候选池必须写明**覆盖不保证**。

## 清单住在哪

推出来并且收敛过的清单放在**本目录**（`references/lang/`），**一个栈一个文件**，文件名＝栈名的全小写（名字里带符号的按约定写：C++ 用 cpp.md）。**这个目录装的是「按技术栈逐册、数量无界」的清单，语言只是其中一族**——界面栈（Web、iOS、设计工具）与它们同类。**入口件不列举有哪些栈**——它只给这个形状（见分发表那一行）。所以这里不再有"名单"这回事：**加一个栈就是放一个文件**。

**状态**只有两个值，但它说的是**来源**，不是质量：**稳定核**＝顺着上面三道问题推出来、且过了收敛检查的；**候选池**＝**核实过的样本**——有人已经把踩过的写下来了，它不是枚举，**也不宣称是照着三道问题推出来的**。清单自己在开头写明是哪种；候选池必须写明**覆盖不保证**——少了这一行，读者会把清单当成穷尽集，而那是一条本包禁止的完整性命题。

**两条成文路径并存，互不代言。** 三道问题是**生成器**，只在"这门语言还没有清单"时负责从零给出方向；候选池是**已经跑出来的样本**，往往比推出来的更具体。把样本说成推导的产物，会让读者以为它是穷尽集的一片——那正是这套东西最该避免的印象。

## 加一个栈

**一步：放一个文件。** `references/lang/<栈名全小写>.md`（C++ 是 cpp.md）。结构照同目录里已有的清单：

- **开头一行写「状态」**——少了它，就没有任何东西把这个文件认出来（校验器会直接报）；
- 首节只写这个栈的工具链命令，并说清它报什么、**它不报什么**；这个栈没有工具链时（如"界面语义"）就写清这件事，别空着；
- 其余按机制分小节，每条一句、能指到具体代码位置；每条尽量写清**哪一类不报**（例外比清单本身更能防误报）。

**别的地方一处都不用改**：入口件按"栈名全小写"这个形状拼路径；这个栈确实没有清单时，分派会给到本件——现场推一份。

**这句"不用改"有边界。** 加一个**栈**（任何语言、任何界面栈）——放文件就完事，因为它落在入口那句话已有的形状里。加一个**不是栈的东西**（设计工具导出的产物、某个协议、数据模型），或者要往目录描述里加**新的触发词**（新的文件扩展名、新的目录约定）——那就不是放文件的事了：**改入口 + 重跑分发回归**。判据只有一句：**它还是"某语言／某界面栈的写法"这件事吗？不是，就得改入口。**

**工具链那节别把「某版本实测」当成结论基准。** 写成「**以你机器上那版为准**」并附**复查命令**（`python -V`、`dart analyze --version`、`$PSVersionTable`、`rustc -V`）——否则版本一动就要重审全册。

**覆盖边界去列目录看，别抄成表。** 这个目录就是真相源（一个栈一个文件）；**任何"现在有哪几册"的名单都必然漂**——本包已经栽过三次写死的数字。审一门没有清单的语言时，**如实写进报告**："该栈无清单，本次按三问现场推的"。

## 编辑规则

加语言、加条目时会反复重新争论的五件事，在这里定一次。

1. **按栈的机制分轴。** 分类轴是这门语言／这个栈的机制（所有权、错误处理、并发、类型系统；界面栈则是定义点、状态、层级、结构、系统偏好）。**「错误处理」是机制轴；「错误处理写得乱」不是**——它把机制和评价混在一起，判起来只能靠口味。作者、来源、风格、"AI 标签"同样不成轴。
2. **不单列"AI 容易写出的坏味道"。** 高频问题只作为**挑条目时的优先级权重**，不成为分类轴——一旦成轴，主体会漂移、随模型过期、泛化性也没了。与 AI 相关的自检住在 `references/discipline.md`。
3. **工具链优先，且例外与条目同等重要。** 编译器、vet、linter、race detector 会报的不重复写；每条尽量写清**哪一类不报**——例外比清单本身更能防误报，这是清单可信度的来源。
4. **只给清单，不给报告契约。** 清单本体不标证据档位、不做简表；档位与四项收尾、条目多时合并简表，都以 `references/contract.md` 为准。清单文件里不再各抄一份。
5. **语言无关的不进清单文件。** 失败路径、结构、垃圾与冗余各有分册，由入口件第二节的分发表分派。
6. **「不报」必须落到代码里能指的形态。** 「循环次数确定且小」「值域已证明在范围内」「已文档声明」这类读起来客观、实质是把判断权交给读者的写法，等于没写条件。要写成能指的位置或形态：**「上界来自源码里的常量（如 `for _, x := range fixedList`）→ 不报；上界来自输入或 `len(slice)` → 报」**。
7. **族通用的条目点一句族名。** 一条判断若在所有语言里都成立（并发语义、构建开关下的断言消失），行首点明它属于哪一族（如"（并发语义，通用）"）——读者一眼看得出这不是本语言特有。但条目仍留在各册，**不抽成公共池**：那会让人追第二份文件。
8. **可判定性分三档，半可判定的必须自报。** **完全可判**＝判据就在代码里，指到位置就能定；**半可判**＝位置指得到，但"这两处是同一语义"要人判；**不可判**＝指不到位置，**不许进清单**。半可判定的条目逐条写明（如"本条需人工确认语义等价"），**不许与完全可判定的混排**——混排会让它看起来像可判的，跟"推断不得与前三类排在一起"是同一条道理。
9. **两条目要能各自指到不同的东西。** 合得起来却分着写的，合并；**文件里需要一段话才说得清"这两节有什么区别"的，就是该合的信号**。
10. **事实性断言必须引规范原文并标版本。** 「某版本起行为是 X」「这个旗标默认关」「这条是 SCxxxx」——凡是**会随版本、平台或时间变**的话，只能从**规范原文或上游源码**抄来，并在条目里带上出处与版本。**引不出的，不许写成断言**：写「待核」，或者不写。别用看起来合理的内容填（判据见 `references/contract.md` 的「会随版本变的事实」）。

## 官方契约那一层：给起手，不给条目

清单的轴不止「语言机制」，还有「**官方 API 的契约**」——零值、默认值、单位、边界、大小写、时区、编码。**这一层数量无界、且随版本漂**，所以**不追全**：

- **每题只收少数常咬点**（每册封顶 4–6 条），形态限于**零值 / 默认值 · 单位 · 边界 · 大小写 · 时区 · 编码**这几类——收的是**形态**，不是把 API 列一遍；
- **其余当场查原文**：那是这一层的仪器（`--help`、官方手册、上游源码）；
- **每条带出处与版本**；查不到写「待核」（规则 10）。

**为什么不写全**：写全必然过时，而且过时是静默的。

## 已知盲区自检

**方法本身不产生这张表。** 每个栈推导完，各自推一张「三问与三道交叉检查漏掉的面」，**放在那一册自己的文件里**（`references/lang/rust.md` 末尾有一张现成的样子）。推导完先拿自己那张对一遍，比再补一轮条目更省。

## 轴外条目：不由本件产生

有一类缺陷不落在"保证 × 逃生舱"的交点上，因此**推不出来，也不要硬推**：

- 惯用型：布尔参数、`Option` 参数、单模式 `match` 该不该换 `if let`、重复绑定该不该用 `@`
- 承诺面：`pub` 铺得过宽、`pub use` 暴露内部路径、feature 是否可加
- 口味与命名

这类条目最强的保证者是**工具链与配置**，不是清单：clippy 的 lint 集、`unreachable_pub`、`cargo hack --feature-powerset`、`cargo-udeps`。把规则放进 lint（机器每次都会想）比放进清单（每次都要人或模型想起来）可靠。推导时遇到这类，明确写"需外部输入"，不要伪装成推导结果。

## 报告

按 `references/contract.md` 收尾：推导出来的每条都要挂全四项——证据档位、最强反方、什么会让我改变结论、刻意没查什么。本件只给推导方法，不给报告形态。
