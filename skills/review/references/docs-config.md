这一组的共同点是：它们描述的都是"声称"，而声称需要证据。凡是写着"兼容""显然""总是""已经支持"的地方，逐个问它的证据在哪。

**这句判据带得出四节，带不出全部。** 文档的可信度、接口契约、数据与状态一致性、时间与确定性四节，由它直接推出。

**「复用既有代码」「跨平台的文本与脚本」两节不由它推出**——它们是经验，不是"声称需要证据"的推论，要**换仪器**：回原文重读那一段、把文档说法执行一遍、拿实际产物对一遍。换起手不算（同一模型的第二遍，见 `references/contract.md` 第一节）。「外部依赖」介于两者之间，只用这一句容易漏，单独过一遍。

这一轮在报告里也有落点：在 `停止审查的依据` 表之后那三行收尾里写 `额外一轮：做了／未做（理由）`。

**本件产出的是评审结论与缺口清单，不是对项目的补写。** 发现"这里缺少说明""这里没有回退方案"是结论；除用户明确要求、或**本次任务本就包含修复**外，不要顺手去补文档、补默认值说明、给方案加时间点。

## 文档的可信度

- 文档里的操作步骤是实测过的，还是凭记忆写出来的？没跑过的步骤要标出来，而不是混在跑过的里面
- 标注为"显然""自然成立""不需要考虑"的断言，其成立条件是否被单独列出来？被省略的条件正是后来出事的地方
- 声称的"兼容"是否附带了具体的测试覆盖？兼容是一个需要证据的词，不是一个形容词
- 对现有行为的描述，是否区分了"我观察到的"和"我推测的"
- **"契约已冻结""测试已通过"都不等于实现满足了契约**：冻结说的是文本定了，通过说的是那批用例覆盖到的部分。要说实现满足，得指到每条条款由哪一处检查承接；指不出，就是"文本有了、承接还没有"
- 文档与代码不一致时，**先判这份文档在说什么**，再判谁错。**规定行为的**（规范、契约、协议）按固定顺序走，不能跳到结论：①**规范自己打不打架**——同一节两版原文、两条要求合在一起要求相反，先把它们合成一条（一条检索、两处并排就够），别拿其中一版去判代码；②**规范一致、代码相反**——不一致是待查，不是文档过时：可能是实现漏了，也可能是规范写错了；说不出哪边是立法意图就写"疑似遗漏"，别拿一边落槌；③**能指出规范依赖的前提今天已不成立**（当初为什么这么定、那条前提在哪一版或哪个 HEAD 上被推翻）——这时才写"该改的是规范"，并把那条前提的出处写出来。**描述实现的**则相反：以代码为准——留着一份错的文档比没有文档更坏
- 文档里的"当前事实"（现在是什么版本、什么已完成、什么还没做）要逐句对当前的 HEAD 与工作树核，不是顺着读——它们写下之后对象一直在动，过期是静默的
- 一份规定"必须／不得／一律"的规范，每条要能指出：判它真假的谓词、代码里的锚点（符号或条款号）、**怎么观察它违反了**（退出码、异常、结构化字段还是日志——都没有就写"无"，那本身是结论）、违反时落在哪条失败路径上——缺一条，它就只是愿望
- 若这份规范是要照着做的（施工依据、改造清单），先验它可执行：同一口径全篇唯一且可判定；它引用的外部条文逐条回源；同一节存在两版原文的先合并；状态只能有一个载体。照抄进施工，矛盾会在改完代码之后才暴露
- **被取代的条文不要删，也不要悄悄改。** 删掉之后，下一个读到的人会把同一条重新提出来（他看不到"这条已经判过"）；留着不标，又会被当成现行。改动时保留原值，标一行"已取代：被哪一条取代、在哪一版或哪个 HEAD 上核过"。判据：读到这一条的人能不能在两句话内知道它不再生效
- 协作或生成过程中残留的痕迹是否已清理：重复段落、前后矛盾的表述、对话残留、被引用但不存在的章节；**过程叙事、勘误叙事（"原先写反了"）、编辑事故（重命名漏改的自指句）这三类也要过一遍**——完整清单在 `references/discipline.md`

## 接口契约

- 输入约束是否与调用方的实际调用方式一致？还是只与接口定义时的假设一致
- 输出是否区分了"稳定字段"与"可能新增字段"？调用方需要知道哪些可以依赖
- 契约里隐含的时序假设（先 A 后 B）是否被显式写出？只靠调用顺序成立的契约会在重构时静默失效
- 同一接口在不同版本间的行为变化是否被记录，且调用方能否检测到变化
- 契约双方的用词是否有各自不同的解读空间？模糊量词能否被换成有明确真值条件的说法
- **"没做完"的三种形态要在结果里分开**：还需人再做（待办）、系统之后会自动做（例如首次挂载时才建 overlay）、本就不必做。出口码相同也要在结构化结果里区分——**静默退出 0 是最坏形态**，脚本无法分辨"全部完成"与"一半完成、剩下的交给启动期"。
- **对外契约有没有版本与兼容上界**：承诺支持到哪个版本、哪种形态为止？没有上界的兼容分支会一直长——每接纳一个旧形态就多一条永久分支。

## 数据与状态一致性

- 同一数据是否在多个位置各存一份？如果是，同步策略与冲突解决规则定义过吗
- **读进来、改一处、整份写回去时，没被读进来的字段去哪了？** 这是"可往返"问题：解析器不认得的字段、版本比当前新的字段、结构里没有对应位置的键，重写时会变成默认值或被丢掉——**落地的字节被静默改掉，没有任何报错**。判据是"逐字段点名：哪些被读进来、哪些原样保留、哪些会被重写"，而不是"解析成功了"。同一形态的两个实例：协议头里没读的版本字段被改写、字符串编码的有损转换（如非法序列被替换成占位符）后再写回整份结构；都不报"转换函数写错了"，而报"这一步没有保真承诺"
- 状态转换的中间态能否被外部观察到？能的话，观察者是否对它产生了依赖——一旦有人依赖中间态，它就不再是实现细节
- 数据格式迁移期间，新旧格式共存时的读写行为是否逐项确认过
- **本工具自己写出的制品有没有版本与"旧版本怎么办"的决定**：版本号写在哪、读到更旧或更新的一版是拒绝且不改，还是兼容读取并就地升级？兼容读取要写明支持到哪个版本为止——每多读一个旧形态就多一条永久分支（上界同「对外契约有没有版本与兼容上界」）。**判据**：拿上一版的制品喂给当前版本，指出它落在哪一支、由哪一行承担。不报：制品是临时文件或运行期缓存，不跨版本存活。
- 启动、关闭、重启时的状态恢复行为是否明确定义并验证过
- 持久化的数据在断电、崩溃或介质损坏后可恢复吗

## 时间、顺序与确定性

- 操作之间的顺序依赖是被显式声明的，还是隐含在代码的偶然执行顺序里
- 是否存在被当作"同时发生"、实际上可能有序先后的两件事？这个顺序差异有没有被建模
- 涉及时间的逻辑，在不同时钟源、不同延迟、乱序下是否验证过行为

## 外部依赖

- 每个引入的依赖，其维护状态、许可证条款、安全公告渠道是否被确认过
- 对依赖行为的假设（例如"这个函数总是返回某种编码"）是否在当前版本实测过，而不是沿用了文档里的说法
- 依赖升级时，是否有一份用于验证兼容性的回归清单
- 若该依赖被废弃或撤回，替代路径和切换成本是否已知

## 复用既有代码

复用时最容易出的事是把原上下文里的假设一起带过来。

- 被复用的组件是否清掉了它原上下文特有、而当前上下文不成立的默认假设
- 继承或扩展的代码是否保留了原始设计意图，还是只复制了它的表面形式
- 模仿某个既有模式时，是否确认了它的适用条件今天仍然成立——"看着眼熟"不是理由
- 从别处搬来的代码是否留下了原项目的命名、路径或术语残留

## 跨平台的文本与脚本

行尾与编码只在**换一个环境执行**时才暴露，而报错信息与真实原因完全脱钩：

- 行尾是否统一：CRLF 进了 Linux 容器，脚本第一行的解释器路径末尾会多出一个不可见字符，报的是"文件不存在"；配置文件则报成语法错误
- 编码是否显式：无 BOM 的 UTF-8 被按 GBK 解析，含中文的脚本直接语法错；反过来，某些宿主**需要** BOM 才能正确识别 UTF-8
- 别指望肉眼：把这两条落成机械检查（`.gitattributes`、门禁脚本），只写在文档里等于没写

## 报告

按 `references/contract.md` 收尾。这一节的问题大多是"声称与证据之间的落差"，所以**依据**尤其要写清：哪一条是你在文档/契约里读到的说法，哪一条是你实际验证过的。

还有一条本册特有的：**位置引用要唯一可定位**。同一份报告里别一会儿裸文件名、一会儿带目录；路径前缀前后一致，行号要给到能直接跳过去的那一处。**定位不到的位置，等于这条结论不可核对**——读者得自己猜你指的是哪个文件的时候，依据和反方都白写了。**二手位置不算位置**：代理或别人给你的行号与文件名，先自己定位一次再写进去；**降档不免责**——依据是给结论的，位置是可核对的事实，错了就是给复核的人埋坑。
