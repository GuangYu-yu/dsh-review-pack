# dsh-review-pack

一个"审一切待交付的东西"的评审技能包：**一个入口技能 + 18 个分册 + 两组按需增长的清单（`references/lang/` 按栈、`references/theme/` 按外观规格）**。

技能本体与宿主无关——`skills/` 下就是普通的 `SKILL.md` 技能集，正文只用 `git` 与通用命令，不调用任何宿主专有工具或服务。任何能读 `SKILL.md` 的宿主都能装；`cordis.patch.yml` 只是给 DSH 的可选装配层，别的宿主忽略它即可。

## 它解决什么

"帮我看看这段改动有没有问题"这句话，模型给不出稳定答案，通常是因为三件事没有约定：**该查哪些面**、**每条结论要交代到什么程度**、**什么时候算查完了**。本包把这三件事写成契约：

- **分发**：入口件按对象把活分派给对应分册，"对象是补丁 → 读 `references/diff.md`"是硬指令，不靠模型自己想起来。
- **依据**：每条结论必须交代它是**读源码**、**跑了命令**、**引了原文**还是**推断**，并给出**最强反方**与"什么会让我改变结论"。
- **收口**：报告固定三段——**发现的问题 / 决策点 / 停止审查的依据**；**决策点**要求把指向同一处的几条收口，并写明两种形态（**同一判断被多路各写一遍** / **替沉默路径做决定的默认值**），都不属于就写"零散问题，逐个修"。

## 装

**任何兼容 `SKILL.md` 的宿主**：把 `skills/review/` 复制到技能根就行。**本包只有一个技能**——语言清单是它 `references/lang/` 下的普通文件，没有第二个目录要配套。

```
<技能根>/
└── review/
    ├── SKILL.md          入口件
    └── references/       18 个分册 + lang/（按栈）+ theme/（按外观规格）
```


**DSH**：可以直接按 bundle 安装本仓库或 Release 里的 `.tgz`。

```bash
pnpm dsh plugin --profile <profile> add <本目录或 .tgz 路径>
```

## `skills/` 里有什么

`review/SKILL.md` 是入口件，只做两件事：**说清分册在哪**，以及**按对象把活分派出去**。它每次评审都会加载，所以刻意写得很薄；判定与交付的规则在 `review/references/contract.md`（**每次都读**），其余按需读 `review/references/` 下的 18 个分册（外加 `lang/method.md`）：

| 分册 | 对象 |
| --- | --- |
| `contract` / `format` | 每次都读：结论怎么挂依据、怎么定级、怎么举证、报告要含什么 / 报告外形 |
| `diff` / `code` / `architecture` | 补丁与变更集 / 一份实现 / 结构与边界 |
| `lang` / `robustness` / `performance` / `security` | 语言写法推导 / 失败路径 / 性能 / 安全 |
| `adversarial` / `verification` | 正确性对抗推理 / 验证本身 |
| `operability` / `docs-config` / `style` / `reasoning` | 运维面 / 文档与配置 / 方案取舍 / 已有结论 |
| `derive` / `discipline` / `intake` | 阶段件：评审开场 / 写改代码与交付前 / 没有现成改动可审时怎么取输入 |

`references/` 顶层是 18 个**有界**分册，另有两个**按需增长**的清单目录：**`references/lang/`**（按技术栈分——语言、界面栈各一册）与 **`references/theme/`**（按外观规格分）；两处各有一个 `method.md` 讲这个目录的颗粒度，它本身也是一册。**文件名就是名字的小写**（`C++` → `cpp.md`、Web 界面 → `web.md`）：**加一个栈只在 `lang/` 里放一个文件，入口与分发表一处都不用改**；`theme/` 的每一册**只在项目声明了那套规格时才加载**，没有声明就不判。清单文件开头必须写「状态」行——那是它被认出来的唯一依据：`references/lang/` 下的文件要么带「状态」行，要么只能是那个方法件，**这条有机器检查兜底**。

**`scripts/` 下只有一个自查器**：`verify-report.mjs`。报告写完后跑 `node scripts/verify-report.mjs <报告文件>`，它只查能机械判真假的东西——块序、两张表同号同条数、用量行自己报的数、账本行的减法、依据与级别的用词、标「严重」有没有独立依据——**不判断一条发现对不对**，也不读被审对象。它零依赖、只用 node 内建，宿主有 node 就能跑；没有就写「校验 未跑」并说明原因，不写等于隐瞒。**它是要求不是机制**：跑不跑由评审者决定，这份包无法核实。

## 已知边界

- **效果只验证到"报告纪律"**：一次 n=1 的对照显示，带本件与不带本件**发现能力没有差别**；差别在报告是否可审计（固定三段、逐条依据与最强反方、决策点收口、不可达结论标"待查"）。所以能声称的是"报告更规范"，**不能声称"评审结论更准"**。**而且这一条有反例**：一次真实评审里本件在手边（整份自查用的都是本件的词——依据、发现清单、覆盖表、未亲验、交接实验），覆盖表仍被虚报成"亲自逐行"而实际一个文件都没读；十一条自查里有三条是本件**逐字写过**的规则。**"报告更规范"是在受控对照里成立的，不是无条件成立。**
- **"该查哪些面"的验证只到选件层**：分发回归验的是"该读哪个文件"；**面本身全不全实测过五册**——`security` 与 `performance` 的节被三次独立推导全部复现；`operability` 与 `docs-config` 各有一节零复现；`adversarial` 的十二节只复现五节，并补出一个缺的面（源与目标重叠时的读写覆盖）。另有分册**用这把尺子问不出来**（小节名本身就是判据，没有可作推导起点的总判据）。
- **级别不保证跨轮次、跨模型可比。** 本件只要求"分级口径要在报告里说清"，**不提供严重程度矩阵**——后果依赖对象域（磁盘工具的越界写与网页应用的越界读不是同一个量级），固定矩阵会在别的对象上给错级别。代价是：换了口径或换了评审者，同一条发现的"严重/一般/待查"可能变。**要跨轮次比，比的是依据与仪器，不是级别**——而这两样报告里本来就带：**依据每条必备；仪器在否定与完整性命题、命令三件套、不稳定事实上必备。**
- **"什么时候算查完"没有停止判据**，只有"边界划清"——报告里的范围要逐格有落点。而**"格子是否属实"分两层**：读了哪些文件在宿主侧有记录（可抽查）；**某个分册里走了哪几节没有任何痕迹**（不可抽查）——节级落点是自报。这是从"无痕迹"走到"有痕迹"，还没走到"可抽查"。
- **不回答放行判断**：本包给的是审计材料，不给"能不能合"的 yes/no。
- **跨宿主未实测**；现有回归全部来自同一模型家族。
- **语言清单是候选池，不是穷尽集**：Rust 与 Go 都标了「候选池」（定义见 `references/lang/method.md` 的「现成清单」），**覆盖不保证**，当检索线索用。
- **Go 清单未经实测对照**：没有拿真实的 Go 改动跑过带 / 不带它的对照。
- **不要和其他评审技能包同时装**：定级轴不同（本件是"确认程度 × 后果"，PR 评论类技能通常是阻断优先级），混起来要人收口。
