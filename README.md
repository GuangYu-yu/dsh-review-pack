# dsh-review-pack

一个"审一切待交付的东西"的评审技能包：**一个入口技能 + 19 个分册 + 两组按需增长的清单（`references/lang/` 按栈、`references/theme/` 按外观规格）**。

技能本体与宿主无关——`skills/` 下就是普通的 `SKILL.md` 技能集，正文只用 `git` 与通用命令，不调用任何宿主专有工具或服务。任何能读 `SKILL.md` 的宿主都能装；`cordis.patch.yml` 只是给 DSH 的可选装配层，别的宿主忽略它即可。

## 它解决什么

"帮我看看这段改动有没有问题"这句话，模型给不出稳定答案，通常是因为三件事没有约定：**该查哪些面**、**每条结论要交代到什么程度**、**什么时候算查完了**。本包把这三件事写成契约：

- **分发**：入口件按对象把活分派给对应分册，"对象是补丁 → 读 `references/diff.md`"是硬指令，不靠模型自己想起来。
- **依据**：每条结论要说清它**从哪来**（读了哪段代码、跑过什么命令与退出码、引了哪份一手原文，还是只是推出来的）、**有多稳**、**什么会推翻它**，以及**刻意没查什么**。
- **收口**：报告按三段讲——**发现的问题 / 决策点 / 停止审查的依据**（分节顺序自定）；**决策点**只问一句"有哪几条会被同一个改动一起消掉"，指不出就直说它们互相独立。

## 装

**任何兼容 `SKILL.md` 的宿主**：把 `skills/review/` 复制到技能根就行。**本包只有一个技能**——语言清单是它 `references/lang/` 下的普通文件，没有第二个目录要配套。

```
<技能根>/
└── review/
    ├── SKILL.md          入口件
    └── references/       19 个分册 + lang/（按栈）+ theme/（按外观规格）
```


**DSH**：可以直接按 bundle 安装本仓库或 Release 里的 `.tgz`。

```bash
pnpm dsh plugin --profile <profile> add <本目录或 .tgz 路径>
```

## `skills/` 里有什么

`review/SKILL.md` 是入口件，只做两件事：**说清分册在哪**，以及**按对象把活分派出去**。它每次评审都会加载，所以刻意写得很薄；判定与交付的规则在 `review/references/contract.md`（**每次都读**），其余按需读 `review/references/` 下的 19 个分册（外加 `lang/method.md`）：

| 分册 | 对象 |
| --- | --- |
| `contract` / `format` | 每次都读：结论怎么挂依据、怎么举证 / 交付物与报告要含什么 |
| `diff` / `code` / `architecture` | 补丁与变更集 / 一份实现 / 结构与边界 |
| `lang` / `robustness` / `performance` / `security` | 语言写法推导 / 失败路径 / 性能 / 安全 |
| `adversarial` / `verification` | 正确性对抗推理 / 验证本身 |
| `operability` / `docs-config` / `style` / `reasoning` | 运维面 / 文档与配置 / 方案取舍 / 已有结论 |
| `derive` / `discipline` / `intake` / `state-space` | 阶段件：评审开场 / 写改代码与交付前 / 没有现成改动可审时怎么取输入 / 要一张状态地图 |

`references/` 顶层是 19 个**有界**分册，另有两个**按需增长**的清单目录：**`references/lang/`**（按技术栈分——语言、界面栈各一册）与 **`references/theme/`**（按外观规格分）；两处各有一个 `method.md` 讲这个目录的颗粒度，它本身也是一册。**文件名就是名字的小写**（`C++` → `cpp.md`、Web 界面 → `web.md`）：**加一个栈只在 `lang/` 里放一个文件，入口与分发表一处都不用改**；`theme/` 的每一册**只在项目声明了那套规格时才加载**，没有声明就不判。清单文件开头必须写「状态」行——那是它被认出来的唯一依据：`references/lang/` 下的文件要么带「状态」行，要么只能是那个方法件，**这条有机器检查兜底**。

**`scripts/` 下四个自查器**，都只查能机械判真假的事、都不判断一条发现对不对，也不读被审对象：`verify-quotes.mjs`（每条 `文件:行号` 落不落得到源文件、反引号引文在锚点附近是否逐字存在）、`ledger.mjs`（账本一张表：列对齐、位置锚点、表头重名、同位置重复；`merge` 合并多本）、`review-check.mjs`（产出目录：只有一份交付物、分过路要有合并后的账本、锚点、分路覆盖；给了范围清单还核越界——报告里的位置要么在清单里，要么那一条自己标了「清单外」）、`check-claims.mjs`（未填的槽位、替读者宣布"通过"的词、"没有遗漏"这类完整性命题）。零依赖、只用 node 内建，宿主有 node 就能跑；没有就写「校验 未跑」并说明原因，不写等于隐瞒。**它们是要求不是机制**：跑不跑由评审者决定，这份包无法核实。

## 已知边界

- **效果只验证到"报告纪律"**：一次 n=1 的对照显示，带本件与不带本件**发现能力没有差别**；差别在报告是否可审计（每条交代来源、最有力的反驳与什么会推翻它，决策点收口，不可达结论标"待查"）。所以能声称的是"报告更规范"，**不能声称"评审结论更准"**。**而且这一条有反例**：一次真实评审里本件在手边（整份自查用的都是本件的词——依据、发现清单、覆盖表、未亲验、交接实验），覆盖表仍被虚报成"亲自逐行"而实际一个文件都没读；十一条自查里有三条是本件**逐字写过**的规则。**"报告更规范"是在受控对照里成立的，不是无条件成立。**
- **"该查哪些面"的验证只到选件层**：分发回归验的是"该读哪个文件"；**面本身全不全实测过五册**——`security` 与 `performance` 的节被三次独立推导全部复现；`operability` 与 `docs-config` 各有一节零复现；`adversarial` 的十二节只复现五节，并补出一个缺的面（源与目标重叠时的读写覆盖）。另有分册**用这把尺子问不出来**（小节名本身就是判据，没有可作推导起点的总判据）。
- **同一条发现的分量不保证跨轮次、跨模型可比。** 本件要求每条写清后果（最坏会怎样、多容易走到）与这条判断有多硬，**不提供严重程度矩阵**——后果依赖对象域（磁盘工具的越界写与网页应用的越界读不是同一个量级），固定矩阵会在别的对象上给错刻度。代价是：换了评审者或换了项目，同一条发现读起来的分量可能不同。**要跨轮次比，比的是依据与仪器**——而这两样报告里本来就带：**来源每条必备；仪器在否定与完整性命题、命令三件套、不稳定事实上必备。**
- **"什么时候算查完"没有停止判据**，只有"边界划清"——报告里的范围要逐格有落点。而**"格子是否属实"分两层**：读了哪些文件在宿主侧有记录（可抽查）；**某个分册里走了哪几节没有任何痕迹**（不可抽查）——节级落点是自报。这是从"无痕迹"走到"有痕迹"，还没走到"可抽查"。
- **不回答放行判断**：本包给的是审计材料，不给"能不能合"的 yes/no。
- **跨宿主未实测**；现有回归全部来自同一模型家族。
- **语言清单是候选池，不是穷尽集**：Rust 与 Go 都标了「候选池」（定义见 `references/lang/method.md` 的「现成清单」），**覆盖不保证**，当检索线索用。
- **Go 清单未经实测对照**：没有拿真实的 Go 改动跑过带 / 不带它的对照。
- **不要和其他评审技能包同时装**：交付口径不同（本件要求每条带来源、反方与否证条件，PR 评论类技能通常先给阻断优先级），混起来要人收口。
