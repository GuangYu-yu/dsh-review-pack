# dsh-review-pack

一个给编码 agent 用的评审技能。

把「怎么审一样东西」写成一套可以照着走的判断方法，再打包成技能的形态交给宿主。此后凡是有人问这些改动能不能合、这段代码有什么问题、这里会不会被搞坏、这个方案值不值得上，它都会被加载进来，让回答按同一套标准交代，而不是想到哪里查到哪里。

要审的东西，从一次变更集、一份实现、一套结构与依赖，到一条失败路径、一道安全边界、一次跨语言移植、一轮验证与门禁，再到运维面、文档与配置、方案取舍，以及自己已经得出的结论。某门语言或某个界面栈另有写法清单，没有清单的栈则给一套现场推导的方法；对象声明了某套外观规格时，另有一份核验它有没有被绕开的清单；改代码、准备宣称完成时，还有一组纪律要先过。这些册子并不平行地摆在一起，而是按「你现在手上是什么」分派，命中的那一册再自己带上它认为必须同读的另外几册，越往下越具体。不做的事也明确：不写新功能，不做逐字翻译，不讨论评审流程本身。最要紧的一条，是不替读者宣布「通过」——一次评审能给的是范围、仪器，和在覆盖范围内未发现什么；能不能放行是读者的事，写进报告就等于把判断悄悄挪给了别人。

在摊开之前，先得把要审的东西定住，这一步不在三步里，但它是三步的前提。手上没有可看的东西时，先把它取到或问出来；有东西但范围没定时，先冻结问题边界——这次审的是哪次改动、哪几条保证、哪些不在范围内——再推该审什么。边界不冻，后面每读一段都会扩一点，最后既收不了口，也说不清停在哪。横轴也不按文件切，按这个对象向外交代了哪几条保证切：按文件切出来的每一路只能交文件级的缺陷，因为那正是它负责的单位；按保证切，才逼得人跨文件追到底。

判据不来自通用清单。通用清单是按「平均的项目」写的，会问到这里根本不存在的东西，同时漏掉这里真正危险的东西，而后者才是值得花时间的地方。所以每类对象各立自己的判据，从它的形态里推：结构问改动会扩散到哪里、实现被替换时外部需要知道多少；失败路径只问每条失败在本系统里有没有真实的触发路径，答「这条走不到」和答「不需要处理」都是正当答案，用不着为了整齐补一个机制；安全收得很窄，只问外部输入进来之后谁说了算，以及秘密的可见面有多大——窄不是省事，是因为判定权一旦跟着数据走，注入、越权和取信错位就都在里面了。

每条结论都要交代清楚：位置在哪，从哪来，有多稳，什么会推翻它，以及刻意没查什么。来源要分得出是读到的代码、跑过的命令与退出码、引的一手原文，还是推出来的；代理转来的话标成转述、并注明还没回源，因为转述和已核在读者那里是两回事。把推断说成观察，比老实承认「这是推的」更坏，读者会因此跳过复核。完整性命题还多一道关：「没有别的调用点」「都已覆盖」这类话，文本搜索证明不了，命中了只说明存在，空结果只说明没发现，所以要连同能证伪它的仪器和具体命令一起交出来，交不出就别据此删改。

写法清单最容易变成一张经验表，见过什么坑就记一条，换一门语言立刻失效。这里从语言的设计承诺往外推：这门语言保证什么，为兑现这个保证牺牲了什么，它开的逃生舱又在哪，缺陷就长在这三者的交点上。清单的第一节先写这个栈的工具链：它报什么、不报什么，条目各落在哪一半；那一节还写「以你机器上那版为准」并附复查命令，因为版本一动，写在纸上的结论就可能过期。外观规格也一样，先判项目到底声明没声明这套规格，没有声明就不判，声明了才问代码绕没绕开。

有些问题不适合按「哪里写错了」来找。对象带持久化状态、恢复路径、多个写者，或者同一事实有多种表示时，先要摆出基线、不变量和维度，看哪些组合构造得出来而语义并不成立。这类问题一处一处地补是补不完的，因为不是某一处写错了，是形状允许它错。正确性对抗也不再是「想到什么报什么」，主线固定为一句话——这段代码在什么输入或什么时序下会做出它不该做的事——然后沿真实执行路径走一遍。目标是最低的误报率，不是最多的发现；触发条件可以是运行时可达，也可以是源码里两处的对照，后者不要求先证明可达，否则能报的就只剩已经复现过的那些。

下面这一段只在对象大到一次读不完时用得上，小对象可以跳过。

这时才派多路。派活之前先按保证切横轴，每一路小到一次读完仍握得住，握不住就沿保证边界再切，不按文件数切。同时建一本账本，一条一行，边读边写，位置一律写成「文件:行号」，因为长任务里前面的发现不是被忘了，是被后面的挤出上下文；再建一份范围清单，一行一个文件，读到就改状态。账本记读到了什么，清单记还该读什么，两者都在盘上，进程被杀之后覆盖到几分之几仍然数得出来。分过路的评审还要一路独立回源复核，逐条核锚点、引文、后果，产出的是判定表，不是第二份报告；再加一路冷读，读的是报告本身。复核路也不免检：从它判成立与撤回的条目里各抽一条重核，抽不出来就说明它也只是转述。如果你只有自己一处上下文，这份分工就免除——自己写、自己核一遍即可，但「自己核过」要照写，它和「有一路独立核过」不是一回事。

能机械判真假的那几件事可以交给脚本：位置落不落得进对象，引文对不对得上，哪些句子写了断言却没给依据。它们只回答对得上对不上，回答不了结论对不对，这一点写在脚本自己的说明里。

反过来，对象小到不值得走全套时，走轻量路径：一处改动、一个文件，不建账本、不派分路、不起冷读，自己读一遍、逐条回源，依据、没查什么、为什么停照写。轻量省的是仪式，不是交代。轻量也不按文件数算，判据是握不握得住、有没有动到收不回来的东西：落在不可逆状态或安全边界上的单点改动，账本可以不建，对抗与实测照叠。实测要留下命令、退出码和结果，结论要能回源；一旦一遍读加自核握不住，轻量就已经不成立，回到有账本、有独立复核的那一档。要不要升级只看一件事——这个对象会不会改动收不回来的东西：持久化存储与布局、数据库、资金、已发布的数据或接口。会，就对抗与实测都在里面，静态推断只能写成「静态未发现破坏路径，动态未验」；判不了就按「会」处理，因为把「不会」说错，代价收不回来，而说「不会」本身不花任何东西。

真正走起来是：先定住对象，再三步——摊开、收口、回头再摊开一次，第二步和第三步之间会回头。

第一步是摊开，刻意不下判断，只回答一件事：这个对象向外交代了什么。不是「它应该有什么」，而是它已经写在类型、签名、注释、文档里的承诺：哪个状态值承诺了会被落盘，哪个参数承诺了按什么单位解释，承诺在哪一句建立，又在哪几处被假定成立。之所以不下判断，是因为人一读就会开始判。读到第三行看见一处空判断，往往就顺着钻下去，收工时手里是一串按阅读顺序排下来的东西——那是检查记录，不是评审。

第二步是收口。摊开之后会有很多「可能有问题」，让它们各自过一道门：能不能说出触发条件和后果，并且指到可核对的东西上。代码问题指到「文件:行号」；性能问题指到共用的那一次调用、那一行；运维问题指到哪条路径、哪份配置、哪条告警；方案取舍指到它服务哪个阶段、它假设的输入成不成立。指不到具体形态、只能说得圆，就是没过门——门要的是能核，不是听起来成立。过了门的按上面那套结构写下来，过不了门的不写，也不作为「仅供留意」垫在报告末尾——那种垫底在读者眼里和真问题是同一个重量。

第三步是回头再摊开一次，最容易被省掉。收口之后，手里有几条确认的问题，和一个解释它们的根；麻烦在于，一个刚好只解释已报上来的那几条的根，便宜得可疑，它通常意味着别的路上有同形的东西，只是那一轮没人走到。所以要把根写成一个能检索的形态——哪类值、哪类调用、哪类边界——再回对象上扫一遍同形的位置，把漏掉的补进来。扫的时候方向是反的：不问还有什么可能有问题，而问哪些观察到的现象在「这里没问题」的假设下说不通；每条说不通的背后都藏着一个隐含假设，把假设一条条拿去证伪，直到新的异常引不出新的假设为止。

这三步落到一个小东西上，是这样走的。某个接口的注释里写着「重复调用是安全的」——这是一句承诺，不是一句判断。第一步只把它记下来，连同它在哪里被假定：重试逻辑假定它，批量导入假定它，上游传来的那个幂等键也假定它。第二步才问，有没有一条路径在第二次调用时做了不该做的事；有，就指到那一行，说出触发条件和后果——同一条记录落了两遍——这条才过门，只能说「并发下可能有麻烦」的没过。第三步再问这个根还会长在哪：同一批接口里，还有几个也这样承诺，却没有人去重。三步走完，手里是一条能核的发现，和一句说得清为什么停在这里的话。

三步走完，报告只答三件事：找到了什么；这批问题共用几个根、哪几条会被同一个改动一起消掉，指不出就说它们互相独立，不必硬凑成一个根；以及凭什么停在这里——哪些没查、哪些查了没结论、为什么查不下去，还有这份报告不证明什么。三条之外不写建议、不写选项、不写下一步动作，那些是读者的事。

这些做法背后是几条不太好绕开的账。最根本的一条是漏和错的代价不对称：留一条错的发现，读者多花几秒钟；静默撤掉一条对的，那条发现就永远消失了，而且没有人会知道它曾经存在。所以撤一条结论只认两种地面，位置不在，或者原文直接相反；「可疑」「看不出来」「价值不高」都不构成撤回的理由，误删最贵的那几类问题——内存安全、并发、声明与定义一致、对外行为变更——恰恰是自信最不可靠的地方。另一条账是凭空造出来的风险从来不是免费保险：一个并不成立的对抗性问题不会安静地消失，它会被当成真实的风险对待，进而逼出防御性代码、多余的检查，以及为假想失败预留的分支；过度工程常常不是写多了，是防了不存在的东西，而把一个自造的风险写进报告，代价由下游承担，承担的人还看不出这笔账是从哪来的。

读者不会把报告里的每一条都重核一遍，实际上他只有两个位置：全信，或者重核。举证结构的作用就是把这两个位置拆开，信得过的跳过，看着不对的那一条当场推翻，不必把整份报告重做一遍；这也是为什么报告里不能出现没有依据的句子，哪怕它听起来很稳妥。停点同样不能靠毅力，「清单翻完了」不是一个停点，清单永远可以再翻一遍，结果要么是无限延长，要么是草率收工；换成「新的异常引不出新的假设」，停不停由对象来回答，不由疲劳回答。报告最后必须写清哪些没查，也是同一个道理：没查的部分和查过没问题的部分，在读者那里是完全不同的两件事，混在一起写，等于用后者替前者担保。

最后是一些刻意放弃的做法。不给后果分级的名词表，因为同一个现象在不同项目里后果不同，拿上一份报告的说法套这一份就会失真；不规定报告的版式，因为读者不同，能否核得动比整齐更重要；不把「通过」写进结论，因为通过与否是读者的事。这些放弃都有代价，省下的确定性要由读者自己补上；但换成一套看起来专业的分级和一句看起来负责的「可以放行」，代价更大，那会让人以为已经处理过了。

还有几件事它做不到，也不打算假装做到。判据是从对象形态推出来的，推得够不够窄、问得对不对，靠写这一册的人和读它的那一刻；流程能让结论交代清楚，不能让判据本身变准，所以效果的上限在判据这一层，不在流程。只有代码这类对象有能指到具体位置的门，性能、运维、方案取舍的门天生要软一些，同一套方法用在这些对象上，效果会明显掉一档。它能防住低级自欺——账本建了、位置写了、复核路被抽过一条；防不住「看起来严谨就行」：账本可以是收工前一次写完的，抽检只抽一条，抽不中照样过，报告格式全对而结论没上去。轻量路径也一样，它是降档的出口，也是逃避全套的出口，从外面看是同一个样子；所以「够不够格走轻量」被列在只能读、不该有闸门的那一栏，而不是被当成可以用规则关掉的事。
